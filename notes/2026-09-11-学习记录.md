## 一、今日学习内容

### 1. Java 基础语法结构

- 程序入口固定写法 `public static void main(String[] args)`
- 类的定义：`public class 类名 { ... }`
- 三种注释：单行 `//`、多行 `/* */`、文档注释 `/** */`
- 输出：`System.out.println(...)`（`System` 是类，`out` 是对象，`println` 是方法）

### 2. 变量与基本数据类型

| 类型 | 占用位数 | 取值范围 | 易错点 |
|---|---|---|---|
| `byte` | 8 | -128 ~ 127 | 超范围赋值直接编译报错 |
| `short` | 16 | -32768 ~ 32767 | |
| `int` | 32 | -2³¹ ~ 2³¹-1 | 整数字面量**默认**是 `int` |
| `long` | 64 | -2⁶³ ~ 2⁶³-1 | 字面量必须加 `L` 后缀，否则超 `int` 范围就报错 |

### 3. 常量与类型转换

- `final` 修饰常量，赋值后不可修改（被注释掉的 `a1 = a1 + 1;` 就是在验证这一点）
- 隐式（自动）转换：**小范围 → 大范围**才自动完成，如 `byte b = a;`（`byte` → `short`）
- 反向转换（大范围 → 小范围）必须显式强制转换，否则编译报错（`a = b;` 报错即为此）

### 4. 与 Python 的知识迁移对比

| 对比项 | Python | Java |
|---|---|---|
| 类型系统 | 动态类型，`a = 1` 直接推断 | 静态强类型，`int a = 1;` 必须声明 |
| 整数精度 | **任意精度**，自动扩容不溢出 | 定长位数，溢出后**静默回绕**（不报错） |
| 位宽意识 | 基本可以不关心 | 必须时刻清楚，是理解补码/溢出的前提 |

> 这个差异是今天最重要的收获：Python 里 `2**100` 直接算得出来，Java 里就必须先想清楚"装不装得下"。

### 5. 二进制与米奇试药问题

「米奇试药」即经典的小白鼠试毒问题：*n* 只米奇能一次性定位出 2ⁿ 瓶药中的毒药——每只米奇代表二进制的一位，喂药方案就是毒药编号的二进制表示。1000 瓶需要 10 只（2¹⁰ = 1024）。

对应到 Java 的知识点是：**位模式既是数值，也是编码**。这为后面学位运算符（`&`、`|`、`^`、`~`、`<<`、`>>`、`>>>`）打下了直觉基础。

### ① 数值范围写错了（两处）✅ 已修正

```java
// 原注释：
// int  类型数据的范围是 2的32次方 到 2的32次方-1
// long 类型数据的范围是 2的64次方 到 2的64次方-1
```

**应为**：
- `int`：**-2³¹ ~ 2³¹-1**（不是 2³²）
- `long`：**-2⁶³ ~ 2⁶³-1**（不是 2⁶⁴）

规律：*n* 位有符号整数的范围是 **-2ⁿ⁻¹ ~ 2ⁿ⁻¹-1**。位数是 32 和 64，指数是 31 和 63。

### ② 「为什么负数不需要 -1」——方向对，表述要收紧 ✅ 已修正

原注释里"补码是反码基础上 +1"这个理解是对的。更准确的表述是：

*n* 位一共产生 2ⁿ 个位模式，划分为：

- 非负：**2ⁿ⁻¹** 个（**包含 0**）→ 因为 0 占掉一个，最大正数只能是 2ⁿ⁻¹**-1**
- 负数：**2ⁿ⁻¹** 个 → 能一直取到 -2ⁿ⁻¹，**不需要减 1**

一句话：**减 1 是因为 0 占了一个坑，不是因为"二进制表达的限制"**。

补码的额外好处：**0 只有唯一一种表示**，省下来的那个位模式就多表示了一个负数——所以 `byte` 能取到 `-128`，正数最大却只有 `127`。这正是「负数比正数多一个」的由来。

> ⚠️ **后续调整（2026-09-11）**：本节③原本补进代码的两行结论注释（拓宽方向链、Java 无 `unsigned`）已从 `LearningData1.java` 中移除，代码里只保留「目标范围 ≥ 源范围」这一条核心规则。**结论本身仍然成立**，此处保留以防遗忘，复习时以笔记为准。

### ③ 「隐式转化要求双方都有符号或无符号」——Java 里不适用 ✅ 已修正

```java
// 原注释：
// 隐形转化的要求：1小范围转化到大范围，2要么双方都有符号，要么双方都无符号
```

**第 2 条是 C/C++ 的规则，不是 Java 的。** Java 的整数类型**全部有符号，没有 `unsigned`**，所以不存在"符号性匹配"的问题。

Java 隐式转换只需满足一条：**目标类型范围 ≥ 源类型范围**。

拓宽方向：`byte → short → int → long → float → double`

> 顺带纠正代码里 `//a=b;` 那行注释：报错原因**不是"数值超出范围"**，而是 `short → byte` 属于「大范围 → 小范围」，编译器在类型层面直接拦下——**只看类型，不看运行时的值**。`b` 是变量而不是编译期常量，所以哪怕它实际存的是 `127`（放得进 byte），这行代码依然编译不过。实测报错信息为「可能有损转换: 从short转换到byte」。

### ⑥ 小建议：用十六进制/二进制字面量

```java
byte a = 0x7F;          // 比 127 更直观地看出"低 7 位全是 1"
int  c = 0b0111_1111;   // 直接对应今天学的位模式
```

十进制的 `127` 看不出位模式，而今天刚学的正是二进制与补码——用进制字面量能把这个知识点接上。

### 修正验证（实测证据）

修正后重新编译运行，全部通过：

```
javac -encoding UTF-8 -Xlint:all src\LearningData1.java   →  exit 0，无警告
java LearningData1                                        →  输出 127
```

另外单独写了一个探针程序，验证「大范围 → 小范围必须强制转换」这条结论确实成立：

```java
short b = 30000;
byte a;
a = b;              // 编译失败
```

实测报错：

```
错误: 可能有损转换: 从short转换到byte
        a = b;
            ^
```

改成 `a = (byte) b;` 后编译通过，运行输出 **`48`**。

> **`48` 是怎么来的**：`30000` 的二进制是 `0111 0101 0011 0000`，强转成 `byte` 只保留低 8 位 `0011 0000`，正好是十进制的 `48`（即 `30000 & 0xFF = 48`）。这直观演示了**强制转换会截断高位**——也是今天学的位模式知识的第一个实际应用。

**延伸验证：变量 vs 字面量，待遇完全不同**

```java
short b = 127;
byte x = b;          // ❌ 编译失败：可能有损转换: 从short转换到byte
```

```java
byte y = 127;        // ✅ 编译通过，运行输出 127
```

同样是"把一个能放进 byte 的值赋给 byte"，**变量不行、字面量可以**。原因：编译器对**编译期常量**能做范围检查（字面量 `127` 在 `-128~127` 内，放行），但对**变量**无法保证它永远在这个范围内，于是只在类型层面判断——`short` 比 `byte` 宽，一律要求显式强转。

这条结论正好反过来印证了前面的话：**编译器看的是类型，不是值。**

### 附：今天踩到的一个环境坑

用 PowerShell 的 `Set-Content -Encoding UTF8` 生成 `.java` 文件时，**会在文件开头写入 BOM 字符**（字节 `EF BB BF`），`javac` 直接报 `错误: 非法字符: '\ufeff'`。

正确写法（不带 BOM）：

```powershell
[System.IO.File]::WriteAllText("X.java", $code, [System.Text.UTF8Encoding]::new($false))
```

或者编译时统一加参数：`javac -encoding UTF-8`。IntelliJ 里写代码不会遇到这个问题，但以后用脚本批量生成代码文件时会。
